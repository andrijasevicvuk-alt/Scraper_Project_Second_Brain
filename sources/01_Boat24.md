# Source — Boat24

## Current status

Boat24 is the first planned vertical slice and broad marketplace backbone for the scraper platform.

The active phase is **`scraper_project Step 4 — source specification`**.

The current repository evidence does **not** show:

- a Boat24 protected acquisition adapter in `scraper_project`;
- approved Boat24 protected configuration;
- Boat24 parser fixtures in `scraper_project`;
- a Boat24 offline parser;
- a live Boat24 pilot;
- a production-approved Boat24 acquisition/parser version.

Therefore this note must not be described as an implemented prototype blueprint yet. It is the working source note from which the Step 4 specification will be finalized.

## Business role

Boat24 is intended to provide broad marketplace coverage for the first complete source vertical.

Step 4 must explicitly finalize:

- in-scope and excluded boat categories;
- geographic scope;
- required and optional YPI source-level fields;
- list-page versus detail-page responsibilities;
- stable source identity requirements;
- source-level output expected at the YPI raw-ingestion boundary;
- known data-quality limitations.

## Historical evidence from YPI

The separate YPI repository contains an older bounded Boat24 draft collector.

Its recorded run:

- attempted direct HTTP search routes;
- received HTTP 403 responses for the tested requests;
- extracted zero listings;
- wrote no production Boat24 dataset.

This evidence is useful because it shows that the tested naive direct-request route was not sufficient under those conditions.

It does **not** establish:

- the current Boat24 defense profile;
- that all direct HTTP clients fail;
- that browser-mediated acquisition is required;
- that a specific anti-bot/session tool is required;
- that Boat24 is unusable.

All current acquisition-route claims remain hypotheses until controlled source experiments are recorded.

## Step 4 specification work

### Identity

Preferred rule:

```text
source_name + stable source_listing_key
```

If Boat24 does not expose a sufficiently stable listing key, the fallback may be a deterministic canonical-URL identity with reduced identity confidence.

The fallback must be documented and approved before Genesis.

### Discovery

Potential entry points/partitions such as category, price and year remain hypotheses until measured.

Step 4 defines what must be discovered and how completeness will be judged. It does not invent a production pagination/partition rule before evidence exists.

### List-level responsibility

The source specification should determine which of these can reliably come from discovery/list pages:

- source listing key;
- listing URL;
- title;
- asking price text;
- currency;
- visible location;
- visible status;
- selected visible specs;
- card fingerprint.

### Detail-level responsibility

The source specification should determine which fields require detail evidence, including where available:

- builder/make;
- model;
- variant;
- year built;
- dimensions;
- engine/propulsion information;
- location;
- ownership/use clues;
- description;
- image URLs/count;
- other valuation-relevant source facts.

Unknown or unavailable fields remain unknown.
